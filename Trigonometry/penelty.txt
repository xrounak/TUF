Issue found in q9: card/illustration clip data-duration ended exactly AT their morphToStack/fadeOut start time, so the transition animation got cut mid-motion when the clip unmounted.

Fix applied (q9 only, not a template-wide rule): extend each affected clip's data-duration by ~1.5-2s past its morph/fade completion time (morph = start+0.8s, fadeOut default ~0.4s), so the transition finishes fully before unmount.

- card-given, card-step1, card-step2, card-step3 durations bumped
- illus-pinned duration bumped (fadeOut at RECENTER_TIME needed room to finish)
- stack-*, options-reveal, q-pinned were already fine (already ran clean to video end or matched exit point)

Check for this same bug on every future question: any clip whose data-duration ends exactly at a morphToStack/fadeOut/pinFlow call needs +1.5-2s buffer past that transition's completion, or the animation will visibly cut off.

Issue found in q10: illustration side/angle text labels got clipped ("Opposite" rendered as "Oppos") because the SVG viewBox was too tight around the label text, and the triangle itself rendered too small at default scale.

Check for this same bug on every future question: size illustration text labels' containing viewBox with enough margin for the full label string at its font-size (don't just fit the geometry), and keep the theta arc's endpoint computed exactly from the true triangle angle (never hand-guess arc endpoint coordinates) so it stays precise even after rescaling.

STANDARD (from q10 onward): render every angle arc with the CSS stroke-dasharray circle technique below, not a hand-built <path> arc. A full <circle> stroked only (fill="transparent"), dash length driven by a CSS custom property --angle (the EXACT angle in degrees, computed via acos/asin/atan from the known sides - never eyeballed), so the visible arc is always precisely theta degrees no matter how the illustration gets rescaled later.

<circle
  cx="VERTEX_X" cy="VERTEX_Y" r="RADIUS"
  fill="transparent" stroke="#4eb85f" stroke-width="8" stroke-linecap="round"
  transform="translate(0, calc(2*VERTEX_Y)) scale(1,-1)"
  style="--angle: THETA_DEGREES; stroke-dasharray: calc((var(--angle) / 360) * CIRCUMFERENCE) CIRCUMFERENCE;"
/>
<!-- CIRCUMFERENCE = 2 * PI * RADIUS -->

The transform vertically flips the circle about its own center so the stroke starts at 0deg (pointing +x, same direction as the adjacent/base ray) and sweeps UP toward the hypotenuse - without it, the default sweep goes clockwise/downward, off the triangle. Apply this to both the full-size Phase 1 illustration arc and the shrunk Phase 2 pinned-icon arc (same technique, smaller radius/circumference).

Issue found in q12: the standard --angle stroke-dasharray circle technique (see above) was written with --angle given a "deg" unit (e.g. "--angle: 45deg"). calc((var(--angle) / 360) * CIRCUMFERENCE) then divides a <angle> by a plain <number> (360) - the deg unit does NOT cancel out, so the calc() result is itself an angle, not the length stroke-dasharray requires. That makes the whole stroke-dasharray value invalid CSS, which the browser silently ignores - the circle renders as a solid, complete ring instead of a partial arc. It looked identical to a correctly-drawn "full circle" bug at a glance, but the root cause was a unit mismatch, not a wrong angle value.

Fix applied (q12): declare --angle as a bare unitless number (e.g. "--angle: 45", not "45deg") everywhere this technique is used - both the full-size Phase 1 arc and the shrunk Phase 2 pinned-icon arc. This matches how CIRCUMFERENCE itself is always written unitless (stroke-dasharray accepts plain numbers as SVG user units).

Also found in q12: GSAP was used to additionally tween the same "--angle" custom property at runtime (`tl.to("#angle-arc", { "--angle": "45deg" }, time)`) on top of the static inline value. Animating a CSS custom property through GSAP's plain .to() is unreliable (no guaranteed unit/interpolation handling for custom properties without registering them), and it duplicated work the opacity fade-in already did. Removed the GSAP tween entirely - the arc's final angle is set once, statically, in the markup; only opacity is animated to reveal it. This is now the standard: do not GSAP-tween the --angle custom property, only fade its opacity in.

Check for this same bug on every future question: when writing the --angle circle technique, always use a bare unitless number for --angle (never "Ndeg"), and never GSAP-tween --angle - only fade the element's opacity.
